#### ISSUE-042 ✅ 완료 — Q15 확정 (2026-07-13)

**주제**
관리자 담당국가 의미 명확화

**배경**
관리자 계정마다 담당국가가 배정되는데, 이 값이 정확히 어떤 의미인지 — 콘텐츠 조회 범위 제한인지, 배정 표시용인지 — 기획에서 확정되지 않은 상태.

**결론**
담당국가는 **수정 권한의 기준**으로 사용됨. 조회(읽기)는 담당국가 무관 전체 가능.

| 담당자 유형 | 조회 | 수정·삭제 |
|------------|------|-----------|
| 담당국가 = 한국 | 전체 국가 콘텐츠 | 전체 콘텐츠 가능. 전체 권한 자동 부여 |
| 담당국가 = 해외 | 전체 국가 콘텐츠 | 자국에서 작성한 콘텐츠만 가능 |

**담당**
기획 확정 → 반영 완료

- 정렬(최신순/오래된순 필터, `sortInquiryList()`) `smartscore_admin_v0.3.html` 반영 완료
- 상태 3단계 — `getInquiryStatus()` 신규 함수로 "진행중" 여부를 저장값이 아닌 **스레드 내 admin 메시지 존재 여부로 매번 계산**. `openInquiryDetail()`/`sendReply()`/`toggleInquiryStatus()` 전부 이 함수를 통해 배지 갱신. 답변 발송 즉시 대기→진행중 전환, 완료 후 재오픈 시에도 스레드에 답변이 있으므로 자동으로 진행중 복귀. 상태 필터 옵션에 "진행중" 추가

#### ISSUE-097 ✅ 완료 — "관련 가이드 연결" 양방향화 + 가이드당 최대 5개 상한 확정 (2026-08-28) — ⚠️ 아래 "폼은 여전히 단일 셀렉트" 부분은 이후 ISSUE-098(검색+선택 콤보박스) → ISSUE-099(폼당 최대 5개 다중 선택)로 대체됨

**주제**
ISSUE-096에서 복원한 "관련 가이드 연결"(단일 셀렉트, 편도)을 다시 검토 — 여러 가이드가 동일한 가이드 하나를 계속 선택할 수 있어 노출 개수가 무한정 늘어날 수 있는 구조적 문제, 그리고 A가 B를 선택했을 때 B 쪽에서도 A가 노출되어야 자연스럽다는 점이 확인됨

**결론**
- **연결은 양방향** — A가 B를 "관련 가이드"로 선택하면 B의 가이드 상세 "함께 보면 좋은 가이드"에도 A가 함께 노출됨(한쪽만 선택해도 서로 연결)
- **가이드 1건당 최대 5개**로 상한 확정 — 관리자 등록 폼은 여전히 1건씩 선택하는 단일 셀렉트지만, 여러 다른 가이드가 같은 대상을 계속 선택하면 그 대상의 연결 수가 누적되므로 정원을 둠 — ⚠️ **폼당 1건 제약은 이후 ISSUE-099에서 폐기되어, 현재는 한 폼에서 직접 최대 5개까지 선택 가능**
- **정원 초과 시**: 이미 5개가 연결된 가이드를 새로 선택하려 하면 "이미 5개의 가이드와 연결되어 있어 추가할 수 없습니다. 연결을 끊고 다시 시도해 주세요." 안내 후 등록/저장 자체를 차단

**코드 반영**
`smartscore_admin_v0.3.html` — `_guideOwnPick`(가이드별로 자기가 직접 선택한 연결 1개) · `_guideRelations`(양방향으로 반영된 전체 연결 집합, Set) 두 구조로 관리. `seedGuideRelations()`로 페이지 로드 시 기존 데이터 기반 양방향 관계 초기화, `linkGuideRelation()`/`unlinkGuideRelation()`로 관계 추가/해제, `isGuideRelationFull()`로 정원 체크. `populateRelatedGuideOptions()`가 정원 찬 대상은 라벨에 "(연결 5/5 가득 참)" 표시. `validateForm('guide')`에 정원 초과 검증 추가, 등록/저장 성공 시 `commitGuideRelation()`이 기존 연결 해제 후 새 연결을 양방향으로 확정(수정 시 대상이 바뀌면 이전 연결은 자동 해제). 가이드 상세 모달의 "관련 가이드" 표시도 전체 연결 목록 + 건수(N/5)로 갱신
`smartscore_cs.html`의 "함께 보면 좋은 가이드" 노출도 `.slice(0, 5)`로 상한 적용

**문서**
`policy_admin.md`·`policy_user.md`의 "관련 가이드 연결"/"함께 보면 좋은 가이드" 조항에 양방향·5개 상한·정원 초과 안내 반영, `confluence_반영본.html` 동일 반영

#### ISSUE-098 ✅ 완료 — "관련 가이드 연결" 목록 선택 + 키워드 검색 동시 지원 (2026-08-28) — ⚠️ 아래 "hidden input 1개" 구조는 이후 ISSUE-099에서 다중 선택 배열(칩 UI) 구조로 대체됨

#### ISSUE-099 ✅ 완료 — "관련 가이드 연결" 폼당 1개 → 폼당 최대 5개로 확장 (2026-08-28)

**주제**
ISSUE-097에서 "가이드 1건당 최대 5개"로 상한을 정했으나, 이는 여러 "다른" 가이드가 같은 대상을 각각 1개씩 선택해 누적되는 구조였음(폼 자체는 여전히 1건만 선택). 사용자가 "가이드가 5개까지 연결될 수 있어야하는데 지금 하나밖에 안 돼!"라고 지적 — 실제로는 **한 가이드를 등록/수정하는 폼 안에서도 직접 최대 5개까지 골라 연결할 수 있어야** 한다는 것으로 확인

**결론**
- **폼당 선택 가능 개수를 1개 → 최대 5개로 확장** — 검색+선택 콤보박스에서 고른 항목이 칩(chip) 형태로 쌓이고, 각 칩의 ×버튼으로 개별 해제 가능
- 총 연결 상한(5개)은 기존과 동일하게 유지하되 계산 기준을 **"자기 폼에서 직접 고른 것 + 다른 가이드로부터 받은 것"의 합산**으로 명확화(양방향 구조상 두 출처가 같은 Set에 합쳐짐)
- 자기 폼에서 이미 5개를 다 채운 경우: 검색창 placeholder가 "최대 5개까지 연결했습니다"로 바뀌고 드롭다운도 안내 문구만 노출 — 더 이상 추가 선택 자체가 불가(폼 자체의 개수 제한이므로 "선택은 허용, 제출 시 차단" 패턴과 달리 즉시 차단이 맞다고 판단 — 다른 가이드 상태에 의존하는 공유 자원 제약이 아니라 이 폼 자신의 로컬 제약이기 때문)
- 대상 가이드가 이미 다른 경로로 5개가 찬 경우의 차단 방식(선택은 허용하되 등록/저장 시 안내 후 차단)은 ISSUE-097 그대로 유지 — 이건 공유 자원 제약이라 즉시 차단하면 다른 가이드 조합 확인이 번거로워짐

**코드 반영**
`smartscore_admin_v0.3.html` — `_guideOwnPick`(문자열 1개)을 `_guideOwnPicks`(배열)로 전환, 폼 편집 중 임시 선택 상태를 담는 `_guideRelatedDraft` 배열 신규 도입. `linkGuideRelation()`이 `_guideOwnPicks[a]`에 push하도록 변경(중복 방지). `relatedGuideCandidates()`가 이미 draft에 담긴 항목은 후보에서 제외. `filterRelatedGuideOptions()`가 draft 5개 도달 시 즉시 안내 문구만 렌더링하고 종료. `selectRelatedGuide()`가 draft에 push(5개 초과·중복 시 무시)하고 검색창 비움, `removeRelatedGuide()` 신규(칩 ×버튼). `renderRelatedGuideChips()` 신규 — 선택된 칩 렌더링 + 5개 도달 시 placeholder 문구 전환. `commitGuideRelation()`을 배열 diff 방식으로 재작성(이전 선택 중 빠진 것만 해제, 새로 추가된 것만 연결). `openGuideRegister()`/`openGuideEdit()`이 draft 배열을 초기화/프리필하도록 수정. `validateForm('guide')`의 정원 초과 검증도 draft 배열 전체를 순회해 정원 찬 대상이 여러 개면 모두 메시지에 나열. HTML에 칩 컨테이너 `#guide-related-selected` 신규 추가, hidden input(`#guide-input-related`)은 draft 배열로 대체돼 제거. CSS `.related-guide-selected`/`.related-guide-chip` 신규 추가

**문서**
`policy_admin.md` "관련 가이드 연결" 행을 "1개 선택"→"최대 5개 선택"으로 갱신, 상한 계산 기준(자기 선택분+타 가이드 선택분 합산) 명확화. `policy_user.md` "함께 보면 좋은 가이드"의 기재 기준·정원 초과 시 행 갱신. `confluence_반영본.html` 동일 반영

#### ISSUE-105 ✅ 완료 — 답변 발송 시 첨부 이미지 미발송 결함 수정 + 메시지 수정 시 이미지 개별 삭제 지원 (2026-08-28)

**주제**
문의 답변 작성 시 이미지를 첨부해도 실제 발송 시 메시지에 포함되지 않고 미리보기 영역에 그대로 남는 결함을 사용자가 발견("이미지 발송이 안되고 그대로 남아있어"). 원인은 `sendReply()`가 텍스트(`ta.value`)만 읽고 `#admin-reply-img-preview`에 쌓인 첨부 이미지는 전혀 참조하지 않았기 때문 — `previewAdminReplyImages()`는 미리보기 썸네일만 그릴 뿐 발송 로직과 연결돼 있지 않았음. 추가로 사용자가 "문의/답변 수정할 때도 이미지 삭제도 가능할 수 있어야 한다"고 요청

- **답변 내용 없이 이미지만 발송하는 것도 허용**(기존엔 텍스트가 없으면 발송 자체가 막혀 있었음)

- 텍스트·이미지 모두 없는 상태로는 저장/발송 불가(최소 하나는 있어야 함)

**코드 반영**
`smartscore_admin_v0.3.html` — `sendReply()`가 `#admin-reply-img-preview`의 썸네일에서 이미지 데이터를 읽어 발송 버블에 `<div class="msg-images right">`로 포함하고 `INQ[...].thread`에 `images` 필드로 저장, 발송 후 미리보기 영역(`imgPreview.innerHTML = ''`) 초기화. 텍스트 없이 이미지만 있어도 발송 가능하도록 검증 조건 완화, 번역 배지도 텍스트가 있을 때만 노출. `openInquiryDetail()`의 관리자 메시지 렌더링에도 동일하게 `m.images` 표시 추가(본문이 없으면 `msg-body` 자체를 렌더링하지 않아 빈 말풍선 방지). `editInqMsg()`를 확장해 편집 중 임시 이미지 목록(`_inqEditImages`)을 두고 `renderInqEditImages()`/`removeInqEditImage()`로 개별 삭제 UI 제공(기존 `.reply-img-thumb` 스타일 재사용), 본문이 없던(이미지만 있던) 메시지도 편집 박스를 이미지 영역 앞에 삽입해 편집 가능하도록 처리. `saveInqMsgEdit()`이 텍스트·이미지 둘 다 없으면 저장 차단.
