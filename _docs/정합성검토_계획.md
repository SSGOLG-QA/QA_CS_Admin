# 정책-구현 정합성 검토 계획 (CS Admin)

> 목표: **실제 구현 사이트 `customer-success-td.smartscore.kr` ↔ 기획서(`_docs/`)** 를 대조해
> 일치/불일치/미구현/미결을 전수 리포트로 산출.
> 검증 축은 경기관제 하네스 2축 전략 재사용: **① PASS/FAIL(구현 기준)** + **② 기획-구현 차이(INFO, `diff`)**.

## 진행 단계

### Phase 0 — 저장소 세팅 ✅ (현재)
- 프로젝트 스캐폴딩(config·auth·lib reporter 이식·csHelpers·docs). 커밋 대기.

### Phase 1 — 접근 & IA 실측 (로그인 필요)
1. `npm install` → `npx playwright install chromium`
2. `npm run auth` — 브라우저에서 **클라우드 수동 로그인**(자격증명은 사용자가 직접 입력) → 세션 저장.
3. `npm run probe:ia` — 실제 사이트 IA·DOM 덤프(`analysis/_ia-probe.json`).
4. 덤프 기준으로 `lib/csHelpers.ts`의 `SIDEBAR_LINK`·`CS_MENU`·`openApp` 성공판정, `auth.setup`의 로그인 URL/판정 셀렉터 **보정**.

### Phase 2 — 화면별 정합성 검증 스위트
프로토타입/기획에서 확정된 규칙(→ `ANALYSIS_기획요약.md`)을 화면별 `run*()` 로 검증.
- 우선순위(구현 확정 영역 먼저): 대시보드 → 공지사항 → 업데이트 → 솔루션 가이드 → FAQ.
- 각 화면: 진입 → 안내문구 `checkText`(전문 일치) → 필드/상태/필터/유효성 `check` → 상수(30블록·50자·5장 등) 경계 → `diff`(기획≠구현) 기록.
- 비파괴 원칙: 저장/삭제/발송 등 데이터 변경 동작은 **노출·활성만** 검증.

### Phase 3 — admin ↔ cs 차등 노출 교차검증
- 같은 콘텐츠가 admin↔cs에서 규칙대로 다르게 노출되는지(반영완료만/날짜라벨/건수 위치 등).

### Phase 4 — 리포트
- `lib/reporter.ts`의 `writeReport()` → `reports/*_report_*.xlsx`(화면별 시트 + 요약 + 기획-구현 차이 + IA + SKIP).

## 검증 컨벤션 (경기관제에서 승계)
1. **리포터 패턴**: `check(page, meta, fn)` / 안내문구 `checkText`. 실패해도 throw 없이 기록 후 계속(전수).
2. **비파괴**: 데이터 변경 클릭 금지. 토글 검증 시 원상복구.
3. **동적 ID 금지**: 채번 id 의존 금지, 섹션/텍스트 스코프.
4. **공백 무시 매칭 / 안내문구 전문 일치**.
5. **2축**: 기능 정상인데 기획과 다르면 AS-IS 검증(PASS) + `diff` 추적(INFO).
6. **데이터 의존 완화**: 개수는 `≥N`, 0건이면 `skip`(사유 명시).

## ⚠️ 제약
- **세션**: 공유 QA 계정 추정 — 동시 로그인 시 강제 로그아웃 가능. 직렬(workers=1) 기본.
- **자격증명**: 자동화가 로그인 자격을 입력하지 않음 — `npm run auth` 헤디드에서 사용자가 직접 로그인.
- **실 DOM 미확정**: Phase 1 실측 전까지 셀렉터/메뉴 매핑은 프로토타입 기준 초안.
