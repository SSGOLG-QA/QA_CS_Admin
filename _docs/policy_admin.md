### 1차 admin 목표 — 게시물 관리

> 완성형 서비스가 아닌 **운영 플로우 검증 + DB 데이터화** 단계

| 항목          | 내용                                                                              |
|---------------|-----------------------------------------------------------------------------------|
| 개발 범위     | 로그인 기능 제외. 운영팀(국내 기준)이 게시물 CRUD 가능한 최소 동작               |
| 사용성 점검   | 프로토타입 완료 시 운영팀 대상 점검 예정 (데이터 저장 불가 안내)                 |
| 점검 항목     | 현재 분류 구조로 운영 가능한가 / 추가 속성이 필요한가                            |

**기술 이슈**

| 항목          | 내용                                                                              |
|---------------|-----------------------------------------------------------------------------------|
| 번역 처리     | 실시간 번역 아님 — **저장형**으로 확정. 플로우: 원본 저장 → 일괄 번역 (마이그레이션 + Batch) → 번역 데이터 저장 |

**기획 보완 필요 (⚠️ 미결)**

| 항목 |
|------|
| 지원 언어 확정 |
| 솔루션 가이드 내 전체 솔루션에 따른 전체 유형 / 전체 분류 항목 확정 |
| 솔루션 가이드 등록 시 제목 생성 태그 — 해외 미지원, 한국어인 경우에만 제공 |
| 해외와 국내의 기능 차이 / 권한 정의 |

| 최초 계정 생성 | 1차 admin 목표 (for 게시물 관리)에서는 계정 관련 개발 작업 미진행                               |

| 로그아웃       | 내부관리자 서비스 로그인 페이지로 리다이렉션 (`https://cc.smartscore.kr/ss/mng/login.html`)     |

**목업 반영 범위 (2026-08-21 정리)**: `smartscore_admin_v0.3.html`은 위 접근 경로 중 **내부관리자 로그인 이후 '고객성공' 메뉴 진입 시점부터**만 다룬다. 그 이전 단계(내부관리자 자체 로그인 화면)는 별도 외부 시스템이라 이 프로토타입 범위 밖 — 이전엔 실수로 **클라우드(cloud.smartscore.kr) 포털 진입 화면**이 admin 파일 최초 화면으로 들어가 있었으나(실제 admin 접근 경로와 불일치) 제거하고, 파일 로드 시 바로 admin 대시보드가 보이도록 정리했다. (cs.html의 클라우드 포털은 고객용 접근 경로가 실제로 cloud.smartscore.kr이므로 별개 — 유지)

## 콘텐츠 에디터

| 항목          | 내용                                                                                          |
|---------------|-----------------------------------------------------------------------------------------------|
| 지원 블록     | heading(제목·구분자) / text(텍스트) / image(이미지) / video(영상)                              |
| 블록 추가 순서 | "블록 추가" 바의 버튼 노출 순서 = 제목 / 텍스트 / 이미지 / 영상 업로드 (2026-08-06 확정, 3개 에디터 공통) |
| 적용 범위     | 공지사항 / 업데이트 / 솔루션 가이드 등록 및 수정 폼                                            |
| **블록 순서 변경 (2026-09-08 확정)** | 각 블록 헤더 좌측 그립 아이콘(⋮⋮)을 마우스로 눌러 드래그하면 블록 영역의 순서를 바꿀 수 있음. 3개 에디터(공지사항/업데이트/솔루션 가이드) 공통 — 텍스트·제목 입력 중 커서 이동이 블록 이동으로 오인되지 않도록 그립 아이콘에서 드래그를 시작한 경우에만 동작 |
| 블록 개수 제한 | 콘텐츠 1건당 **전체 블록 타입 합산 최대 30개**(2026-08-06 변경 — 기존 "이미지 블록만 최대 10개" 제한 폐기). 도달 시 블록 추가 버튼 자체를 차단 + 토스트 "블록은 최대 30개까지 추가할 수 있습니다." 안내 |

## ⚠️ 미결 — 콘텐츠 다국어 번역 정책

> 지원 언어 확정 후 논의 예정. 백로그 1순위 참고.

### 배경

고객이 조회하는 국가에 따라 공지사항·업데이트·솔루션 가이드의 제목·본문·태그·이미지 설명(캡션)이 해당 국가 언어로 표시되어야 함.

### 결정 필요 항목

| # | 항목               | 상태    | 내용                                                                                            |
|---|--------------------|---------|-------------------------------------------------------------------------------------------------|
| 1 | 번역 시점          | ✅ 확정 | **저장형** — 원본 저장 → 일괄 번역 (마이그레이션 + Batch) → 번역 데이터 저장. 실시간 번역 아님 |
| 2 | 태그 번역 방식     | ⚠️ 미결 | 태그는 검색·필터 키로 쓰이므로 단순 문자열 번역 불가. 마스터 테이블에 언어별 컬럼 구조 필요 (`tag_id \| tag_name_ko \| tag_name_en \| tag_name_th \| ...`) |
| 3 | 번역 검토 주체     | ✅ 확정 | **자동 번역 + 관리자 검토·수정 병행**(2026-08-28 확정 — ISSUE-100). 진입 경로: 상세보기 하단 버튼 영역(모달 푸터, "닫기 · 번역 수정 · 수정" 순서 — ISSUE-106)의 "번역 수정" 버튼. 원문(KO)은 등록/수정 화면에서만 수정 가능. **번역이 아직 없는("번역 미입력") 언어에는 버튼 미노출**(2026-08-28 확정 — ISSUE-107, 수정할 대상 자체가 없으므로). **"번역 수정" 클릭 시 원문과 동일하게 블록(제목/텍스트/이미지 설명) 단위로 분리해 보여줌**(2026-09-01 확정 — ISSUE-109) — 블록마다 원문(회색 참고용)과 번역 입력란이 짝지어 노출되며, 업데이트는 솔루션 섹션이 여러 개일 수 있어 각 블록에 `[솔루션명]` 라벨을 함께 표시. (등록/수정 폼에 별도 "번역 검수" 버튼·모달을 두는 방식도 한때 검토됐으나 불필요하다고 판단해 제거 — ISSUE-110) |
| 4 | 번역 엔진          | ✅ 확정 | **Google Cloud Translation 사용 확정**(2026-08-27 — DeepL 제안은 채택하지 않음). 오라클 클라우드 자체 번역 서비스는 비용·품질 측면에서 별도 검토 대상으로 남아있으나, 현재 확정된 엔진을 바꾸는 사항은 아님(인도네시아어 번역 미지원 등 품질 이슈는 참고로 계속 추적) |
| 5 | 신규 국가 추가 시  | ⚠️ 미결 | 기존 등록 콘텐츠에 해당 언어 번역 버전 없음 → 일괄 번역 요청 플로우 필요 |
| 6 | 이미지 설명(캡션) 번역 여부 | ✅ 확정 | **번역 대상에 포함**(2026-08-27). 이미지 설명도 고객 화면에 그대로 노출되는 텍스트라, 제목·본문만 번역하고 이미지 설명만 한국어로 남으면 다국어 문서 안에서 일관성이 깨짐. 최대 50자(2026-09-08 변경 — 기존 20자)로 짧아 번역 비용·처리 부담도 미미. 제목·본문과 동일하게 저장형(등록·수정 시 일괄 번역)으로 처리 |
| 7 | 원문 수정 시 기존 번역 처리 | ✅ 확정 | **원문(제목/본문) 재번역 후 전체 덮어쓰기 유지**(2026-09-02 확정) — "번역 트리거"(등록·수정 저장 시 재번역) 정책상 제목·본문 중 한 글자라도 바뀌면 해당 콘텐츠의 전체 언어가 다시 번역되어 기존 번역을 대체한다. 이는 "번역 수정"(#3)으로 관리자가 직접 손본 번역도 예외 없이 포함 — 별도 병합·보존 로직은 두지 않음. **대신 수정 폼 진입 시 안내 배너로 사전 고지**(신규 등록 시에는 미노출): ① "제목이나 {내용/가이드 내용/솔루션별 업데이트 내용}을 한 글자라도 수정하면 전체 언어가 다시 번역됩니다" 일반 안내, ② [번역 수정]으로 직접 다듬은 언어가 있을 때만 "이미 [번역 수정]으로 직접 다듬은 언어가 있습니다(EN 등) — 원문을 수정하면 그 내용도 함께 사라집니다" 경고 추가 노출. **요청 범위는 이 안내 배너까지**(2026-09-02) — 저장 시 기존 번역을 실제로 지우는 동작은 요청되지 않아 구현하지 않음(한때 [165]에서 추가했다가 오해로 확인되어 제거). 한편 그 외 필드(날짜·상태·국가·솔루션 등)의 수정 저장 미반영 결함은 별도 후속 과제로 분리(아래 "수정 저장 시 실제 반영" 참고) |

### 수정 저장 시 실제 반영 범위 (2026-09-02 확정 — 결함 발견 및 1차 수정)

공지사항/업데이트/솔루션 가이드의 "수정 저장"이 그동안 폼에 입력한 값을 실제 데이터·목록 테이블에 전혀 반영하지 않고 있었음(모달만 닫히고 "저장되었습니다" 토스트만 노출 — 재번역 안내 배너 기능을 테스트하던 중 사용자가 직접 발견). 등록(신규)은 정상 동작하며, **수정(기존 항목 저장) 경로에서만 발생하던 결함**.

| 항목 | 정책 |
|---|---|
| 1차 반영 범위 | **제목·본문(내용/가이드 내용/솔루션별 업데이트 내용)만 우선 반영**(2026-09-02 확정) — 나머지 필드(게시 기간, 노출 여부, 적용 국가, 솔루션, 버전, 유형/분류/태그 등)는 여전히 저장해도 반영되지 않음. 후속 논의로 확장 예정 |
| 반영 방식 | 저장 시 ① 메모리상 데이터 객체(`_currentNotice`/`_currentUpdate`/`_currentGuide`) ② 목록 테이블 행의 제목 텍스트 ③ 그 행의 클릭 핸들러에 박혀 있는 데이터까지 3곳을 함께 갱신 — 이 파일이 별도 데이터 배열 없이 각 행에 데이터를 직접 담아두는 구조라 셋 다 갱신해야 재조회 시에도 값이 유지됨 |
| 번역 연동 | **없음** — "결정 필요 항목" #7의 재번역 정책은 수정 폼의 안내 배너로만 고지되며, 이 저장 반영 작업에서 번역을 실제로 지우는 동작은 넣지 않음(요청 범위 밖으로 확인되어 제외, 2026-09-02) |
| 가이드 제목 변경 시 | 가이드 제목은 "관련 가이드 연결"·FAQ 지정의 식별 키로도 쓰이므로, 제목을 바꾸면 그 연결·지정도 새 제목으로 함께 이전(끊어지지 않음) |

### 수정 저장 시 재번역 확인 알럿 — 공지사항·업데이트·솔루션 가이드 공용 (2026-09-08 확정)

"결정 필요 항목" #7의 재번역 안내는 그동안 수정 폼 진입 시 배너로만 고지됐는데(사전 고지), **[저장] 버튼을 누르는 실제 커밋 시점**에도 한 번 더 명시적으로 확인받도록 확인 알럿을 추가한다. 배너를 안 읽고 지나쳤더라도 저장 직전에는 반드시 인지하고 되돌릴 수 없다는 사실까지 확인하게 하려는 목적. **처음엔 솔루션 가이드에만 적용했다가, 같은 조건으로 공지사항·업데이트에도 동일하게 확장 적용**(2026-09-08).

| 항목 | 정책 |
|---|---|
| 노출 조건 | **① 제목 또는 본문이 실제로 바뀌었고 ② 적용 국가에 한국 외 다른 나라가 포함된 경우에만** 아래 문구로 교체 — 두 조건 중 하나라도 아니면(변경 없음, 또는 적용 국가가 한국 단독) 기존 공통 저장 확인 문구("저장하시겠어요? / 수정된 내용이 즉시 반영됩니다.") 그대로 노출 |
| "본문" 판정 기준 | 공지사항 = 내용, 솔루션 가이드 = 가이드 내용, 업데이트 = 솔루션별 섹션 전체(솔루션·내용 배열) — 업데이트는 섹션 추가/삭제/내용 변경 중 하나라도 있으면 변경으로 간주 |
| 적용 국가 판정 기준 | 상세에 저장된 적용 국가 표시값 기준(3종 공통) — `🌍 전체` 또는 `~ 외 N개`는 항상 포함으로 간주, 국가가 1개뿐이면 그 국가가 한국이 아닐 때만 포함 |
| 문구(제목) | `수정된 내용이 있습니다.` (질문형 아님 — 확인 질문은 설명 마지막 문장으로 이동) |
| 문구(설명) | 3줄로 노출(`white-space:pre-line`): `적용 국가에 한국 외 다른 나라가 있어 저장 시 전체 언어가 다시 자동 번역됩니다.` / `(수동으로 다듬은 번역도 포함)` / `저장 이후 이전의 내용으로 복구할 수 없습니다. 저장하시겠습니까?` — 확인 질문은 마지막 문장. 콘텐츠 종류별 문구 분기 없이 3종 공용 |
| 버튼 라벨 | 이 케이스에서만 기본 `등록` → **`저장하기`**로 교체(그 외 케이스는 기존 `등록` 그대로) |
| 표시 위치 | 기존 저장 확인 모달(`modal-register-confirm`)을 그대로 재사용 — 별도 알럿을 새로 만들지 않고 제목·설명·버튼 라벨만 조건부로 교체 |
| 취소 시 | 모달을 닫고 수정 폼으로 돌아감(입력값 유지) — 기존 저장 확인 모달과 동일 |
| 적용 범위 | 공지사항·업데이트·솔루션 가이드 수정 저장 공통. 신규 등록(저장이 아닌 등록)에는 적용하지 않음 |

### 이미지/파일 첨부 개수 초과 시 공통 알럿 규칙 (2026-08-05 신규)

첨부 개수가 허용 한도를 초과하면 초과분은 첨부하지 않고 즉시 안내한다. 기존에 이미 첨부된 파일은 그대로 유지된다.

| 화면 | 허용 개수 | 초과 시 동작 |
|------|-----------|---------------|
| 문의 답변 이미지 첨부 (admin) | 최대 5장 | 알럿 안내 후 초과분 제외 |
| 새 문의 접수 첨부파일 (cs) | 최대 5개 | 알럿 안내 후 초과분 제외 |
| 추가 문의 입력 이미지 첨부 (cs) | 최대 5장 | 알럿 안내 후 초과분 제외 |
| 공지사항 / 업데이트 / 솔루션 가이드 콘텐츠 블록 (전체 타입 합산) | 최대 30개 | 토스트 안내 후 블록 추가 자체를 차단 |

- 다중 파일 선택형(첨부 버튼으로 여러 파일을 한 번에 선택하는 방식)은 **알럿(alert)** 으로 안내
- 블록 추가형(버튼 클릭으로 블록을 하나씩 추가하는 콘텐츠 에디터)은 **토스트(toast)** 로 안내하며, 한도 도달 시 블록 추가 버튼 자체가 더 이상 동작하지 않음

### 동일 파일 중복 첨부 방지 (2026-09-08 확정)

위 3개의 다중 파일 선택형 첨부(문의 답변 이미지 첨부 admin / 새 문의 접수 첨부파일 cs / 추가 문의 입력 이미지 첨부 cs)는 **이미 첨부된 파일과 이름·용량이 모두 같은 파일을 다시 첨부하려 하면 차단**한다.

| 항목 | 정책 |
|---|---|
| 판별 기준 | 파일명 + 파일 크기(byte)가 모두 동일하면 같은 파일로 간주. 실제 바이트 내용 비교(해시 등)는 하지 않음 — 같은 파일을 다시 선택하는 흔한 실수를 막는 데 충분하고, 매 첨부마다 파일 전체를 읽어야 하는 비용을 피할 수 있음 |
| 안내 문구 | 이미지 전용 첨부(admin 문의 답변, cs 추가 문의 입력): `이미 첨부된 이미지입니다.` / 이미지+영상 혼합 첨부(cs 새 문의 접수): `이미 첨부된 파일입니다.` — 기존 형식·용량·개수 초과 알럿과 함께 목록으로 노출(예: "첨부할 수 없는 파일이 있습니다.\n\n이미 첨부된 이미지입니다.") |
| 비교 대상 | 같은 첨부 영역 안에서 **현재 첨부돼 있는 파일들**과 비교. 삭제(×)한 파일은 비교 대상에서 제외되어 같은 파일을 다시 첨부 가능 |
| 적용 범위 밖 | 공지사항/업데이트/솔루션 가이드 콘텐츠 블록의 이미지 블록은 블록 1개당 이미지 1장을 넣는 구조라 "여러 장 중 중복" 개념이 적용되지 않아 이번 범위에서 제외 |

- **미결 사항**: cs.html 국가·언어 선택기를 11개국 국가 선택기로 교체할지, 언어별 대표 국가 1곳으로 근사할지 결정 필요(ISSUE-079)

### 알림 종류 (6종 확정 — 2026-08-19 "공지사항 등록"·"업데이트 등록" 2종 신규 추가)

| 유형 | 트리거 | 클릭 시 이동 |

| 신규 문의 | 고객 접수 기준 **건별로 각각** | 문의/답변 페이지 진입 + **해당 문의 상세 자동 오픈** (`goToInquiry()`) |
| 답변 대기 누적 | 미답변 문의 **1건 이상**, 각 **30분 이상** 대기(2026-08-19 변경 — 기존 "3건 이상" 임계치 폐기). 알림 문구엔 **실제 대기 건수를 그대로 노출**(예: "미답변 문의 5건 누적") — 고정 임계치 문구 아님 | 문의/답변 페이지 진입, **상태 필터 "답변 대기"가 적용된 목록**으로 이동 (특정 1건이 아닌 목록 전체 대상이므로 상세로 이동하지 않음, `goToInquiryWaitingList()`) |

- 답변 대기 누적 / 공지 만료 예정 / 배포 완료 / 공지사항 등록 / 업데이트 등록은 그대로 **유형당 슬롯 1개 — 새 이벤트 발생 시 이전 알림을 교체**
- Q30(개발 제안: "답변 대기"를 알림함에서 제외하고 대시보드로만 이관)은 **반영하지 않음** — 대시보드는 해당 페이지를 열어야 보이지만 알림함은 어디서든 즉시 환기 가능해야 하므로 유지 확정
- 알림함(30분)과 대시보드 지표 카드(24시간 경과 건수)는 목적이 달라 **서로 다른 시간 기준을 그대로 유지**한다 — 알림함은 즉각적인 환기용, 대시보드 지표는 장기 방치(SLA) 파악용 (2026-08-05 확정)

### 삭제 후 재발생 규칙 (2026-08-06 신규)

X 버튼 또는 클릭(읽음 처리)으로 알림을 지운 뒤, 같은 조건이 여전히 유효할 때 다시 뜨는지에 대한 규칙.

- **이미 알렸던 대상은 재발생하지 않는다** — 예: "답변 대기 누적" 알림을 지운 시점에 조건을 충족했던 문의들은, 계속 대기 중이어도 다시 알리지 않음(이미 인지한 것으로 간주)
- **단, 그 이후 새롭게 조건을 충족하는 대상이 생기면 그 대상 기준으로 다시 알린다** — 예: 알림을 지운 뒤 새로 접수된 문의가 30분을 넘기면, 그 새 문의를 기준으로 "답변 대기 누적" 알림이 다시 발생
- "공지 만료 예정"도 동일 — 지운 공지가 아직 만료되지 않았다면 그 공지로는 다시 알리지 않고, 다른 공지가 새로 D-1 조건을 충족할 때만 재발생
- 신규 문의는 건별 누적형이라 이 규칙이 해당되지 않음(각 건이 독립적인 알림)

### 정렬 순서

각 알림의 **발생/갱신 시각 기준 최신순**으로 정렬 (유형별 고정 순서 아님)

### 읽음 처리

- 알림 클릭 시 해당 알림만 읽음 처리(안읽음 점 제거) + 위 "클릭 시 이동" 경로로 이동
- 상단 "모두 읽음" 버튼으로 전체 일괄 읽음 처리 가능 — **단, "모두 읽음"은 안읽음 표시만 제거할 뿐 알림 항목 자체를 삭제하지 않는다.**
- **실제 데이터 상태가 바뀌어도(예: 답변 대기 건수가 줄어듦) 알림은 자동으로 사라지지 않는다** — 아래 "보관 기간" 규칙(7일 경과)에 해당하지 않는 한, 관리자가 의도적으로 읽거나 X로 지우기 전까지는 "그 시점에 발생했던 이벤트의 기록"으로 남아있음 (2026-08-06 재확인)
- 삭제 방식(읽음 처리 vs X 버튼)의 유형별 차이는 아래 "알림 삭제 방식" 참고

### 보관 기간 — 알림 자동 소멸 (2026-08-19 확정, 기존 "정보성 1회 이벤트형만 X로만 삭제" 정책 폐기)

**모든 알림 유형은 읽음/안읽음 여부와 무관하게, 최초 노출 시점 기준 7일이 지나면 알림함에서 자동으로 사라진다**(목록에 더 이상 노출되지 않음). 기존엔 "액션 필요형(신규 문의/답변 대기 누적)은 읽기 전까지 무기한 유지, 정보성 1회 이벤트형(공지 만료 예정/배포 완료)만 자동 소멸 없이 X가 유일한 삭제 수단"으로 유형별로 달랐으나(2026-08-06), **전체 유형 공통으로 7일 자동 소멸 규칙을 적용**하는 것으로 변경한다.

- 기준 시점은 "최초 노출 시점"(알림이 처음 생성된 시각) — 읽음 처리했다고 리셋되지 않고, 안 읽었다고 연장되지도 않음
- 7일 이내라면 기존과 동일하게 읽음 처리(클릭)나 X 버튼으로 수동 삭제 가능
- 신규 문의 같은 누적형 알림도 각 건이 개별적으로 생성 시각을 가지므로, 건별로 7일이 지나면 그 건만 개별 소멸(다른 건에는 영향 없음)

### 실시간 반영 범위 (2026-08-06 확정)

알림함·대시보드가 서로 다른 시점의 데이터를 보여주면 운영자가 혼란을 겪으므로, **알림함과 대시보드는 동일한 실시간 데이터로 갱신**된다. 내부 admin 사용자 수가 적어(1차는 국내 담당자만) 실시간 갱신의 부하는 크지 않다고 판단.

| 구분 | 갱신 방식 |
|------|-----------|
| 문의 목록이 바뀌는 이벤트(신규 문의 접수, 답변 완료 처리 등) | 서버가 실시간으로 갱신 데이터를 전달 (구체 기술은 개발 착수 시점에 결정 — 웹소켓/SSE 등) |
| "30분 이상 대기" 같은 시간 경과 계산 | **클라이언트 로컬 타이머**로 계산 — 서버 왕복 불필요 |
| 대시보드 지표 카드 | 알림함과 동일한 실시간 데이터로 갱신 |

### 문의 상세 스레드 실시간 반영 (2026-09-08 범위·트리거 확정 → 2026-09-14 구현 방식 확정: 푸시 아닌 10초 폴링)

위 "실시간 반영 범위"는 목록/대시보드 단위였고, 이번엔 **이미 열려있는 문의 상세 스레드 자체**로 범위를 넓힌다. cs/admin 어느 쪽이든 상대방이 새 메시지를 보냈을 때, **보고 있는 화면을 재클릭·새로고침하지 않아도 스레드에 바로 반영**되어야 한다는 요구가 있었다.

| 항목 | 정책 |
|---|---|
| 트리거 1 | admin이 특정 문의 상세를 열어둔 상태에서, 그 문의에 **고객이 새 메시지(신규 문의 최초 접수 포함)를 추가로 보내면** 스레드에 반영 |
| 트리거 2 | cs.html(내 문의/골프장 문의)에서 고객이 특정 문의 상세를 열어둔 상태에서, **admin이 그 문의에 답변을 발송하면** 스레드에 반영 |
| 함께 갱신되는 것 | 상세가 열려있지 않은 경우에도 목록의 마지막 메시지 시각·정렬 순서·상태(답변 대기→진행중 등)·알림함·대시보드는 기존 "실시간 반영 범위" 규칙대로 갱신(변경 없음) |
| 구현 방식 (2026-09-14 확정) | **웹소켓/SSE 등 서버 push 방식이 아니라, 클라이언트가 일정 주기로 새 메시지 유무를 확인하는 폴링 방식**으로 확정. 열려있는 문의 상세 스레드 기준 **10초 주기**로 확인(최초 30초로 검토했다가 체감 지연을 줄이기 위해 10초로 조정) |

### 알림 삭제 방식 (2026-08-19 갱신 — 유형별 자동 소멸 차등 폐기, 7일 공통 규칙으로 통일)

**모든 알림 유형에 X(삭제) 버튼을 제공**한다 — 일부 유형에만 있으면 UI가 비일관적으로 보이므로 전체 유형에 동일하게 적용. 자동 소멸 방식은 더 이상 유형별로 다르지 않고 **전체 유형 공통으로 7일**(위 "보관 기간" 참고)이며, X 버튼은 7일을 기다리지 않고 즉시 지우고 싶을 때 쓰는 수단이다.

| 유형 | 분류 | X 버튼 | 기본 소멸 방식 |
|------|------|--------|----------------|
| 신규 문의 | 액션 필요형 | ✅ 제공 | 클릭(읽음 처리 + 상세 이동)해서 처리하는 게 기본. **7일 경과 시 자동 소멸**(공통 규칙). X는 즉시 삭제하는 보조 수단 |
| 답변 대기 누적 | 액션 필요형 | ✅ 제공 | 위와 동일 |
| 공지 만료 예정 | 정보성 1회 이벤트형 | ✅ 제공 | **7일 경과 시 자동 소멸**(공통 규칙). X는 그 전에 즉시 삭제하는 수단 |
| 배포 완료 | 정보성 1회 이벤트형 | ✅ 제공 | 위와 동일 |
| 공지사항 등록 | 정보성 1회 이벤트형 | ✅ 제공 | 위와 동일 |
| 업데이트 등록 | 정보성 1회 이벤트형 | ✅ 제공 | 위와 동일 |

- 액션 필요형은 "클릭해서 실제로 처리"하는 흐름이 기본이고, X 버튼은 보조적 수단(빠르게 넘기고 싶을 때)으로 함께 제공
- X 버튼 추가에 따라 안읽음 표시(dot)는 기존 알림 우측 위치에서 **알림 아이콘 우측 상단(아이콘 위 오버레이)** 로 이동 — X 버튼과 위치가 겹치지 않도록

### 표시 형식

- 알림 시각: 분 전 / 시간 전 / **1일 전** / N일 전 / MM.DD / YY.MM.DD (2026-08-05 확정 — "어제" 대신 "1일 전"으로 통일. 문의 목록의 상대시간 표기와는 별개 규칙)
- 하단 "전체 알림 보기" 링크 제거 (별도 전체 알림 페이지 없음 — 드로어가 전체 알림 목록 역할을 겸함)
- ⚠️ 확인 중: 벨 아이콘 배지를 있음/없음(dot) 대신 **안읽은 개수 숫자**로 표시할지 결정 필요

### 빈 상태 (2026-08-05 신규)

알림이 하나도 없을 때(전체 4종 모두 발생 이력 없음), 알림함 목록 영역에 안내 문구를 표시한다: **"새로운 알림이 없습니다."**

| 관리자 답변   | 작성 언어로 표시. `{언어} 발송 내용 보기 ▾` 클릭 시 발송된 번역 내용 토글 노출 — **신규 발송 답변뿐 아니라 기존에 이미 번역 발송된 답변에도 동일하게 적용**(2026-09-22 확정. 이전엔 새로 보낸 답변에만 토글이 있고, 기존 답변은 "OO로 번역 후 발송됨 ✓" 배지만 있어 실제 발송 내용을 확인할 수 없었음). 답변 대기·진행중 상태의 메시지는 날짜 옆 **"⋮" 더보기 아이콘**을 통해 **수정**·**회수**를 드롭다운으로 제공(아래 "관리자 발신 메시지 회수·수정" 참고) |

### 관리자 발신 메시지 회수·수정 (2026-08-28 확정 — ISSUE-101, 1차 구현 / 2026-09-02 답변완료 상태 정책 추가)

관리자가 이미 발송한 답변에 오탈자·오안내가 있는 경우를 대비해, 발신 메시지에 대한 최소한의 회수·수정 기능을 1차로 제공한다.

| 항목 | 정책 |
|---|---|
| 노출 위치 (2026-09-22 변경, 같은 날 상시 노출로 재조정) | 문의 상세 스레드 — 관리자(admin) 발신 메시지의 **날짜 옆 "⋮"(세로 점 3개) 더보기 아이콘**. 아이콘은 항상 노출되며(최초엔 메시지 호버 시에만 나타나도록 했으나, 평소엔 자리가 비어 보인다는 피드백으로 상시 노출로 변경), 클릭하면 "수정"·"회수" 드롭다운이 펼쳐짐(기존엔 메시지마다 두 버튼이 항상 노출돼 정보가 많아 보인다는 피드백으로 변경) |
| 수정 | 메시지 본문을 인라인 textarea로 전환해 직접 고쳐 저장. **첨부 이미지는 개별 삭제(×)만 가능 — 신규 이미지 첨부 UI는 제공하지 않음**(1차 범위 제외, 2026-09-04 재확정). 텍스트는 그대로 두고 이미지만 삭제하는 것도 가능(2026-08-28 확정). 저장 시 메시지 옆에 `(수정됨)` 표기 노출(수정 이력·이전 내용은 별도 보관하지 않음 — 1차 범위) |
| **수정 시 최소 1개 유효성 검사 (2026-09-04 확정)** | 저장 시점에 **본문 텍스트와 이미지가 모두 0개면 저장 차단**, 토스트 `메시지 내용 또는 이미지가 최소 1개 있어야 합니다.` 노출 후 저장 취소(수정 박스는 유지, 편집 상태 그대로 남음). 예: 이미지 1장만 있던 메시지에서 그 이미지를 삭제(×)하고 텍스트도 비운 채 저장을 누르면 이 안내가 뜨고 저장되지 않음 — 답변 작성(신규 발송)의 "본문 또는 이미지 최소 1개" 규칙과 동일한 기준을 수정에도 적용 |
| 회수 | 확인 팝업("메시지를 회수하시겠어요? 회수하면 고객 화면에서도 즉시 삭제되며, 이후 되돌릴 수 없습니다.") 후 확정. 회수된 메시지는 관리자·고객 화면 모두에서 본문 없이 `회수된 메시지입니다` 플레이스홀더로만 표시 |
| 회수 후 되돌리기 | 불가 — 재발송하려면 새 답변을 다시 작성해야 함 |
| **답변완료 상태에서 회수·수정 가능 여부 (2026-09-02 확정)** | **불가(N)** — 문의 상태가 `답변 완료`가 되면 모든 관리자 발신 메시지의 "수정"·"회수" 버튼이 노출되지 않는다. 재오픈(`완료 처리` → `재오픈`)해 `답변 대기`/`진행중`으로 되돌리면 다시 노출됨 |
| **회수·수정 권한 범위 (2026-09-02 확정)** | **수정 = 작성자 본인만 가능** / **회수 = 담당 권한이 있는 관리자 누구나 가능**(휴가·부재 대응). 수정은 원 발신자 이름을 유지한 채 내용만 바뀌므로 타인이 수정하면 오귀속(misattribution) 위험이 있어 작성자 전용으로 제한. 회수는 내용을 남기지 않고 `회수된 메시지입니다`로 완전히 가리는 동작이라 오귀속 위험이 없어 개방 — 부재중인 동료의 오답은 다른 관리자가 회수하고 본인 이름으로 새 답변을 재발송하는 방식으로 대응. **단, 관리자 계정/로그인 시스템이 아직 없어(2차 범위, "관리자 계정" 섹션 참고) 발신자가 항상 동일 인물로 시뮬레이션되는 현재 프로토타입 단계에서는 코드로 의미 있게 구현할 수 없음 — 관리자 계정 기능 도입 시 `authorId` 비교로 실제 반영 예정** |
| cs.html 반영 | 고객 화면 문의 상세 채팅에서도 동일하게 회수된 CS팀 메시지는 `회수된 메시지입니다`로, 수정된 메시지는 `(수정됨)` 표기로 노출(`policy_user.md` 참고) |
| 1차 범위 제외 | 수정 이력(변경 전 내용) 보관, 회수 사유 기록, 특정 시간 이후 회수 제한 등은 이번 범위에서 제외 — 필요 시 추후 논의. **"누가 수정/회수했는지" 이름 노출(예: `(수정됨 · OO)`)도 관리자 계정 시스템 도입 전까지는 진행하지 않기로 확정(2026-09-02)** — 수정 권한을 작성자 전용으로 제한한 것으로 오귀속 문제는 해소된다고 판단 |

### 번역 정책

번역은 **관리자(CS팀) 언어와 고객 언어가 다른 경우에만** 적용한다.

**admin 측 동작**

| 조건                          | 동작                                                        |
|-------------------------------|-------------------------------------------------------------|
| 작성 언어 ≠ 고객 언어         | 자동 번역 후 발송. `자동 번역 후 발송` 배지 노출            |
| 작성 언어 = 고객 언어         | 번역 없이 원문 발송                                         |
| 고객 원문 → 관리자 표시       | 항상 한국어로 자동 번역하여 표시. `번역 보기` 토글로 확인   |
| 관리자 발송 내용 확인         | `발송된 번역 내용 보기` 클릭 시 발송된 번역본 토글 확인     |

**cs.html(고객) 측 동작**

| 대상                  | 노출 방식                                                                 |
|-----------------------|---------------------------------------------------------------------------|
| 고객이 작성한 문의    | 번역 없이 원문 그대로 노출                                                |
| CS팀 답변             | 고객 언어로 번역된 결과 노출 + **"원문 보기 ▾" 토글**로 원문(한국어)을 접어서 함께 제공(2026-09-22 확정 — 기존 "원문 미노출" 원칙에서 변경. 즉시 번역되는 일반적인 답변 포함 전체 적용) |
| 관리자 언어 = 고객 언어 | 번역 없이 원문 그대로 노출                                              |

### 번역 지연·실패 시 노출 방식 (Q60, 2026-09-22 확정)

발송은 즉시 처리되고 번역은 뒤에서 별도로 처리된다(위 "번역 정책" 참고). 번역 API가 실패하면 **5회까지 자동 재시도**하며, 그 사이 고객 화면에 무엇을 보여줄지가 이 절의 대상이다. **이 정책은 문의 답변에만 적용되며, 공지사항·업데이트·솔루션 가이드 등 다른 콘텐츠의 번역 정책(원문 비노출 원칙)에는 영향을 주지 않는다.**

| 상태 | cs.html 노출 |
|---|---|
| 번역 진행 중(재시도 포함) | **"번역 중"**(2026-09-22 문구 수정 — 기존 "번역 준비 중"에서 축약) 안내만 노출. 원문·번역본 모두 미노출, "원문 보기" 토글도 없음 |
| 번역 완료 | 번역본 노출 + 위 "CS팀 답변" 행과 동일하게 **"원문 보기 ▾" 토글**로 원문 확인 가능(별도 예외 아님 — 일반 답변과 동일 처리) |
| 5회 재시도 모두 실패 (번역 대기로 확정) | **번역 실패**하며 **원문만 노출**(번역본 없음, 토글도 없음 — 이미 원문이 그대로 보이고 있어 접을 대상이 없음). **"번역에 실패해 원문으로 표시돼요"** 라벨을 원문 말풍선 아래에 배치(2026-09-22 확정, 같은 날 문구 수정 — 최초 "번역 실패 · 원문"은 관리자용 에러 로그 같은 어투라는 피드백으로 고객 화면에 맞는 대화체로 변경). API 연동 오류 등 수정 배포 전까지는 번역을 못 구하므로, 답변 자체를 아예 못 보는 것보다는 원문이라도 보여주는 것으로 확정 |

## cs.html 개선사항 (2026-07-13 반영)

### 공지사항 상세 — 본문 동적 렌더링

- `showNoticeDetail(sol, title, date, expire, content)` 5번째 파라미터 `content` 추가
- `content`는 `\n` 구분 텍스트; 줄별로 `<p>` 태그로 변환, 빈 줄은 `<br>`
- URL은 `linkifyText()` 함수로 자동 링크화 (`<a href="..." target="_blank">`)
- 공지 목록 각 항목에 `content` 인자를 인라인으로 전달

### FAQ 아코디언 토글

- `.faq-q-row`에 `onclick="toggleFaq(this)"` 추가
- 클릭 시 상위 `.faq-item-card`에 `.open` 클래스 토글
- `.open` 상태에서 `.faq-a-row`, `.faq-foot` 노출, `.faq-chevron` 180° 회전

### 새 문의 접수 유효성 검사

- 솔루션(`#inq-sol`), 제목(`#inq-title`), 내용(`#inq-body`) 필드 id 추가
- `submitInquiry()` 함수: 각 필드 빈값 검사 → `.error` 클래스 + `.inq-form-error` 노출
- 유효 시 alert 후 폼 초기화 → `myinquiry` 페이지로 이동

### 문의 목록 → 상세 이동

- `inq-row`에 `onclick="showInquiryDetail(data, fromPage)"` 추가 (myinquiry / gcinquiry 양쪽)
- `data` 구조: `{sol, title, date, status, submitter?, messages: [{from, text, time}]}`
- `status`: `'wait'` = 답변 대기, `'progress'` = 진행중, `'done'` = 답변 완료
- 상세 뷰: `inq-detail-card` 내 thead (배지+상태+제목+날짜) + thread (사용자/CS 메시지 버블)
- 뒤로가기: `backToInqList(fromPage)`로 목록 복원

### 문의 상세 뒤로가기 방식 (Q42/Q43, 2026-08-19 확정)

**결정: 페이지 단위 뒤로가기** — 여러 문의를 옮겨 다니며 열어봤더라도, 뒤로가기는 항상 "직전 상세" 대신 **목록으로 한 번에 복귀**한다. 문의 처리는 콘텐츠 브라우징이 아니라 "목록 → 상세 확인/답변 → 목록 복귀 → 다음 건" 흐름의 업무 화면이라, 열어본 항목 수만큼 뒤로가기를 눌러야 하는 방식(문의 단위 뒤로가기)은 불필요한 클릭만 늘림. 알림·관련 문의 클릭처럼 목록 없이 특정 문의로 바로 진입하는 경로와도 일관되게 동작(진입 경로 불문 뒤로가기 = 목록)

- **cs.html**(내 문의/골프장 문의): `showInquiryDetail()`에서 `history.pushState()`로 상세 진입을 기록, `popstate` 발생 시 `backToInqList()`로 목록 복귀. 상세 화면의 "← 목록" 버튼도 `goBackFromInqDetail()`을 통해 동일하게 `history.back()` 경로를 타 히스토리 스택을 정합하게 유지
- **admin 문의 관리**는 목록(좌)·상세(우) **상시 분할 화면(split-pane)** 구조라 "목록↔상세 페이지 전환" 자체가 없음 — 뒤로가기 정책은 cs.html에만 해당

### 알림·관련 문의로 특정 문의 진입 시 필터 초기화 (Q42, 2026-08-19 확정)

**결정**: 알림함 클릭이나 "관련 문의" 배너 클릭처럼 목록을 거치지 않고 특정 문의 1건으로 바로 진입하는 경우, **진입 전 걸려있던 국가/골프장/상태/정렬 필터를 전체 기본값으로 초기화**한다. 필터를 유지하면 진입 대상이 그 필터 조건에 안 맞을 수 있어(예: "완료"로 필터링해둔 상태에서 "대기" 문의 알림 클릭), 목록에서 대상이 아예 사라져 보이는 문제가 있었음. "답변 대기 누적" 알림처럼 특정 카테고리 전체를 보여주는 목적의 진입(`goToInquiryWaitingList()`)은 예외 — 그 경우는 의도적으로 해당 필터를 적용한 채로 진입

### 홈 버튼 연결

### 홈 탭 필터링 (업데이트 섹션)

## 이미지 확대 보기(라이트박스) 기능 (2026-07-22 반영)

전 화면 딤 오버레이 + 확대 이미지를 보여주는 공용 라이트박스. **조회(열람) 시점에만 적용**하며, 등록/작성(첨부 전 미리보기) 단계에는 적용하지 않는다.

| 구분 | 적용 범위 | 비고 |
|------|-----------|------|
| cs.html | 문의 상세 스레드 이미지 — 고객 본인이 보낸 이미지 + 관리자가 전달한 답변 이미지 (내 문의 / 골프장 문의 양쪽) | `showInquiryDetail()`→`renderInqThread()`에서 `m.images[]` 렌더링. `sendInqReply(idPfx)`로 답변 전송 시 첨부 미리보기 이미지가 스레드 메시지에 포함되도록 연결 |
| cs.html | 공지사항 상세 본문 이미지 | `showNoticeDetail()` content 문자열 내 `[img]<url>` 줄을 `<img>`로 렌더링 |
| cs.html | 솔루션 가이드 상세 본문(`#doc-body`) 이미지 | `doc.body` raw HTML 내 `<img>` 직접 포함 가능 |

### 첨부 이미지 2장 이상 — 좌우 넘겨보기 (2026-09-08 확정)

한 메시지에 첨부된 이미지가 **2장 이상인 경우에만** 라이트박스에 좌우 화살표 버튼과 `N / M` 카운터를 노출해, 닫지 않고도 같은 메시지의 다른 첨부 이미지를 이어서 볼 수 있다.

| 항목 | 정책 |
|---|---|
| 적용 범위 | 문의 스레드 메시지의 첨부 이미지만(admin `.msg-images`, cs `.chat-msg-images`) — 공지사항/솔루션 가이드 본문처럼 낱개로 삽입되는 이미지는 애초에 "같은 메시지의 여러 장"이라는 묶음 개념이 없어 해당 없음(항상 카운터·화살표 미노출) |
| 노출 조건 | 클릭한 이미지가 속한 첨부 그룹의 이미지 수가 2장 이상일 때만 화살표·카운터 노출. 1장이면 기존과 동일하게 화살표 없이 이미지만 확대 |
| 이동 방법 | 좌우 화살표 버튼 클릭만 지원(2026-09-08 확정 — 키보드 `←`/`→`는 추가하지 않음) |
| 순환 방식 | 마지막에서 다음으로 가면 첫 장으로, 첫 장에서 이전으로 가면 마지막 장으로 순환 이동(끝에서 막히지 않음) |
| 이동 범위 | 같은 메시지에 첨부된 이미지끼리만 이동 — 스레드의 다른 메시지 이미지로는 넘어가지 않음 |
| 구현 | `openImgLightbox(target)`이 클릭된 `<img>` 엘리먼트를 받아 `closest('.msg-images')`(admin) / `closest('.chat-msg-images')`(cs)로 같은 그룹의 이미지 src 목록을 구성 — 공지/가이드 본문처럼 그룹이 없는 단일 이미지는 문자열 src를 그대로 받아도 동작(하위 호환) |

## 국가 / 골프장 - ⚠️ 1차 admin 목표 (for 게시물 관리) 미진행

### 목록 컬럼 (Q40, 2026-08-19 확정)

| 컬럼     | 내용                                        |
|----------|---------------------------------------------|
| 국가     | 국가 플래그 + 국가명                        |
| 골프장 수 | 해당 국가 등록된 골프장 총 수              |
| 대기 중  | 현재 답변 대기 문의 건수 (amber)            |
| 진행중   | 답변을 1회 이상 했으나 완료 처리하지 않은 문의 건수 (blue) — 문의/답변 페이지의 "진행중" 상태와 동일 기준(Q29) |
| 완료     | 처리 완료 문의 건수 (green)                 |
| 주요 언어| 해당 국가의 **자동 번역 언어**(Q4 국가별 언어 매핑 기준) — 국가당 언어 1개로 단일 표기(예: 태국 = "태국어") |

- **담당자 컬럼 삭제**(2026-08-19 확정) — 1차 범위에서는 관리자 계정별 담당국가 지정 기능 자체가 미진행(`관리자 계정` 정책 참고)이라 표시할 실데이터가 없어 제거
- **진행중 컬럼 신규 추가**(2026-08-19 확정) — 기존엔 대기 중/완료 2개뿐이었으나, 문의 상태가 이미 대기/진행중/완료 3단계(Q29)로 확정돼 있어 이 화면도 동일하게 3단계로 통일
- 펼쳤을 때(아코디언) 하위 골프장 상세 표의 컬럼이 이 목록과 같은 위치에 오도록 정렬(아래 "골프장 상세" 참고), 펼쳐진 상태는 목록 행 호버와 구분되는 배경으로 표시

### 골프장 상세 (아코디언)

> 국가 행 클릭 시 하위 골프장 목록이 펼쳐짐.

| 컬럼    | 내용                    |
|---------|-------------------------|
| 골프장  | 골프장명                |
| 전체 문의 | 누적 문의 총 건수      |
| 대기 중 | 현재 미답변 문의 건수   |
| 진행중  | 답변을 1회 이상 했으나 완료 처리하지 않은 문의 건수 (blue) — 위 국가 목록 "진행중" 컬럼(Q29 기준)과 동일 |
| 완료    | 완료 처리된 문의 건수   |

- **진행중 컬럼 신규 추가**(2026-09-22) — 상위 국가 목록엔 이미 대기 중/진행중/완료 3단계가 있었는데(Q40), 골프장 단위로 펼치는 이 상세 표만 완료/대기 중 2단계로 남아있던 것을 통일. `전체 문의` = `대기 중` + `진행중` + `완료` 합으로 일관되게 맞춤
- **컬럼 순서**: 전체 문의 → 대기 중 → 진행중 → 완료 (2026-09-22 확정 — 문의 처리 흐름 순서와 동일)
- 상위 국가 목록과 컬럼 위치를 맞춰, 펼쳤을 때 대기 중·진행중·완료가 같은 자리에 오도록 정렬
